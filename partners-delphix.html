The thesis

Three problems, one cause

A bank runs two or three production environments — and somewhere north of a hundred non-production ones: development, QA, UAT, performance, staging, training, regression, cloud testing, analytics sandboxes, disaster recovery rehearsal. A telco, with larger datasets, often runs more.

Almost every one is a full physical copy of production. Real customer names, account numbers, national identifiers and balances — sitting outside production's controls, reached by testers and contractors, and refreshed rarely enough to also be out of date.

The same set of copies is simultaneously the largest concentration of personal data in the organisation, the largest storage line item outside production, and the single biggest constraint on release velocity. Three problems that usually sit with three different executives, and one shared cause.

The bad actor leveraged their knowledge of technical systems, along with specialised tools and capabilities, to gain access to our testing environments.

How it works · Virtualisation

Copy once. Provision instantly, forever.

Delphix separates the data a database reads from the storage that database owns. Everything else follows from that.

01

Ingest once

Delphix takes a single copy of the source using the database's own native backup path — Oracle RMAN, SQL Server backup, VSS. No agent in the transaction path, no schema change, no write to source.

02

Stay in sync

From then on it pulls only changed blocks, continuously. The golden copy tracks production in near real time, and block history is retained rather than overwritten.

03

Provision without copying

Delphix presents a filesystem to the target server over NFS or iSCSI whose blocks point back to the golden copy. The database mounts it and starts as an ordinary, writeable database.

04

Copy-on-write

When a virtual database writes, the shared block is untouched — a new block is allocated, visible only to that environment. Ten environments diverge independently while sharing almost everything.

05

Rewind and refresh

Because block history is retained, any environment can be reset to current production, rewound to a point in time, or bookmarked and branched — in roughly the time it took to create.

06

Self-service

Exposed through a portal and an API — engineers provision, refresh and rewind their own environments without a ticket, and CI/CD pipelines do the same on every build.

How it works · Masking

Two problems — and the second is where most in-house efforts come undone

In an organisation with thousands of tables accumulated over decades, nobody holds a complete map of where personal data lives. Automated discovery finds it by name and by content pattern. Masking it consistently is the harder half.

Irreversible

Not encryption — there is no key, so there is nothing to steal and no route back to the original value. A masked estate cannot be un-masked by anyone who obtains it.

Deterministic

The same input always produces the same output — otherwise one customer becomes three different people across three tables.

Referentially consistent

A surname in a DB2 transaction table and the same surname in a PostgreSQL refund table must mask to the same substitute value, so joins still return the same rows.

Format-preserving

A masked identifier must still pass validation; a masked date must still be a date, and still fall in a plausible sequence — or the application misbehaves for unrelated reasons.

Why masking programmes tend to fail

Rarely because a field cannot be scrambled. Usually because the scrambling breaks referential integrity — joins return nothing, and a large part of the test suite fails for reasons unconnected to the release. Testers conclude the environment is unusable, and before long an exception is granted for an unmasked copy. The control is not defeated so much as routed around.

A useful diagnostic: ask whether non-production is masked, then ask how many exceptions to that policy are currently open.

Before and after, for one engineer's ticket

Before
Monday

An engineer needs a current copy of a core system database to reproduce a defect that only appears at production data volumes. A ticket is raised. It queues behind the database team's change window.

Thursday

Several terabytes of tier-one storage are provisioned and justified. The restore runs overnight. Because the copy is unmasked, either an exception is granted, or a masking job runs, takes most of a day, and breaks several foreign key relationships.

The following Tuesday

The environment is delivered. It is a week old, consumed several terabytes, holds millions of real customer records, and will not be refreshed for months. Two other teams are quietly sharing it.

After
Tuesday, 09:02

The engineer provisions a virtual database from that morning's masked golden copy through the self-service portal. Under three minutes, a few megabytes. Referential integrity is intact, so the application behaves as it does in production.

Tuesday, 11:40

A migration script corrupts the data. Rather than raising a ticket, they rewind the environment to 09:02 in under three minutes and continue — then bookmark the exact data state that reproduces the defect for a colleague.

Wednesday, 02:00

The CI pipeline provisions fresh masked environments for the regression suite via API, runs against them, and tears them down. No one is involved.

A question worth putting to your own teams: how long does it take an engineer to get a current, compliant copy of production — from asking to having it? Most organisations have never measured it.

Regulatory context

De-identification for secondary use, across APAC

Privacy legislation across the region has converged on one principle: personal data used for testing, development and analytics should be de-identified. Non-production is where that principle is most often unmet.

Malaysia

Personal data protection legislation with strengthened obligations and enforcement, alongside central bank technology risk expectations covering data handling across the estate.

Indonesia

Personal data protection law with substantial financial penalties, applying squarely to personal data held in test and development environments.

Singapore

Personal data protection legislation together with technology risk management guidelines expecting robust access control wherever sensitive information is held.

Philippines

Data privacy legislation whose requirements around lawful processing and retention apply to non-production copies as much as to production systems.

Australia

Privacy legislation under reform, alongside prudential standards requiring classification of information assets by sensitivity — a classification non-production copies frequently escape.

Cross-border

Where operations or customers extend to China or India, national frameworks mandate de-identification before secondary use, with penalties that can reach a percentage of annual revenue.

General context rather than legal advice. Obligations vary by organisation, licence and activity — your privacy and legal functions should confirm what applies.

Scope

What it is, and what it is not

✗Accelerate production

It is a non-production platform and doesn't sit in the production transaction path — which is also why it's safe to deploy. Ingest uses the database's own backup mechanism.

✗Federate or virtualise queries

It creates full, writable copies. It doesn't query data in place across distributed sources — for real-time federated analytics, that's a different category of product.

✗Replace your backup strategy

Rapid recovery is a proven use case and recovery times are dramatically shorter, but it complements backup and archival rather than substituting for them.

✗Remove the need for DBAs

It removes the repetitive part — restores, refreshes, the ticket queue. Platform and source administration remain.

✗Preserve real values when masked

By design. Any test that genuinely requires real customer values remains a governed exception with a named approver — a stronger control than a blanket copy.
